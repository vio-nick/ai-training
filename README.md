# 骨质疏松骨折风险 AI 预测模型

本仓库用于开发“骨质疏松骨折风险 AI 预测模型”的研究原型。项目以**骨质疏松性骨折**为直接预测终点，拟融合步态、足底压力、骨密度等仪器测定数据，以及年龄、性别、BMI、既往骨折史、吸烟饮酒史、跌倒史和家族史等非仪器临床指标，构建可解释、可复现并面向基层筛查的轻量化多模态风险评估方案。

> 当前仓库处于项目设计与模型开发准备阶段。尚未包含可运行的训练代码或数据集；文档中的“拟”“计划”均表示项目目标，不代表已验证的临床性能或可直接用于诊疗。

## 项目目标

1. 基于 PRISMA 流程开展系统综述，梳理“步态/足底压力/可穿戴数据 + AI + 骨质疏松或骨折风险”研究中的数据来源、特征、算法、性能和局限。
2. 将综述证据转化为结构化特征字典，筛选同时兼顾预测价值、临床合理性和采集成本的最小候选特征集。
3. 构建并公平比较可解释基线模型与多模态融合模型；在数据条件允许时比较特征级、决策级和混合融合策略。
4. 使用交叉验证及可获得的独立/公开数据开展验证，报告判别能力、校准能力、临床阈值表现和模型解释。
5. 输出适用于社区及家庭场景的轻量化筛查原型说明，包括最小特征集、传感器/输入要求、推理接口和适用边界。

## 研究范围

| 内容 | 计划纳入 |
| --- | --- |
| 主要预测终点 | 骨质疏松性骨折风险 |
| 仪器测定数据 | 步态时空参数、足底压力指标、骨密度（如腰椎、髋部、股骨颈 T 值） |
| 非仪器指标 | 年龄、性别/绝经状态、BMI、既往骨折、吸烟饮酒、跌倒史、家族史等；以研究方案确认的特征字典为准 |
| 候选算法 | 逻辑回归、随机森林、XGBoost 等可解释或轻量级模型；必要时再探索轻量级深度学习模型 |
| 融合方式 | 特征级融合、决策级融合、混合融合；仅在数据模态和样本量支持时实施 |
| 可解释性 | 特征贡献、校准与错误分析；可使用 SHAP 等方法，但不将其视作因果证据 |

跌倒风险在相关研究中可作为骨折的代理终点，用于系统综述与补充分析；本项目的主模型不应在未记录理由的情况下把它替代为骨折终点。

## 所需工作与交付物

### 1. 需求与数据准备

- [ ] 确认目标人群、骨折定义、预测时间窗、纳入排除标准和主要评价指标。
- [ ] 根据系统综述建立 `docs/data_dictionary.md`：字段定义、单位、来源、采集方式、缺失处理和采集成本。
- [ ] 确认公开数据集或经审批的临床数据的许可、伦理状态与访问规则。
- [ ] 编写数据读取、去标识化检查、质量检查、缺失值处理和特征构造流程。
- [ ] 固化按个体隔离的训练/验证/测试切分，建立数据版本、随机种子和环境记录。

### 2. 建模与比较

- [ ] 建立可解释基线（如逻辑回归）和树模型基线（如随机森林、XGBoost）。
- [ ] 比较单模态与多模态输入，以及可行的融合策略。
- [ ] 控制特征选择、标准化、插补和调参仅在训练数据内完成，排查数据泄漏。
- [ ] 对类别不平衡、缺失模态和潜在偏倚制定明确处理与敏感性分析方案。

### 3. 验证、解释与轻量化

- [ ] 采用交叉验证评估候选模型；有独立数据时进行外部验证。
- [ ] 报告 AUROC、AUPRC、灵敏度、特异度、F1、校准曲线、Brier score 与阈值选择方法。
- [ ] 进行特征贡献、错误案例和亚组表现分析，记录模型局限。
- [ ] 形成模型卡与轻量化筛查说明：最少输入、性能取舍、运行资源、适用人群和禁止用途。

### 4. 研究成果

项目申请书的预期成果为以下至少一项：申报一项知识产权、完成并投稿一篇综述，或参加“挑战者杯”等创新竞赛。模型仓库需要为这些成果提供可追溯的实验记录、图表和方法说明，但不会以未经验证的模型性能作为对外结论。

## 技术路线

```text
系统综述与临床定义
        ↓
特征字典与数据可得性核验
        ↓
数据质量控制、去标识化与固定切分
        ↓
单模态/传统基线模型
        ↓
多模态融合模型比较
        ↓
交叉验证、外部验证（如可行）、校准与解释
        ↓
最小特征集 + 轻量化推理方案 + 模型卡
```

## 评价原则

模型选型不以单一最高 AUC 决定。候选模型应在相同数据切分上比较，并综合考虑：

- 临床终点与标签质量；
- 判别能力与校准能力；
- 特异度/灵敏度及阈值下的实际筛查负担；
- 外部可推广性、亚组公平性和数据缺失情况下的稳健性；
- 特征获取成本、模型复杂度和基层场景的可部署性；
- 可解释性、复现性及已知局限。

## 数据安全与研究边界

- 不提交未经批准、未去标识化或不允许在仓库内共享的原始数据、个人身份信息、访问令牌、私有权重或受限文献全文。
- 所有个体级数据须在满足伦理审批、数据使用协议和去标识化要求后使用。
- 公开数据也必须遵循其许可证、引用要求和再分发限制。
- 本仓库中的模型为研究原型，不构成医疗器械、诊断建议或临床决策依据；临床应用需经过独立验证、伦理与监管评估。

## 计划目录结构

随着代码进入开发阶段，建议采用以下结构；如实际结构调整，应同步更新本文档。

```text
.
├── docs/                 # 研究方案、数据字典、模型卡、实验与决策记录
├── configs/              # 可复现实验配置
├── src/                  # 数据处理、特征、模型、评估和推理代码
├── tests/                # 单元测试与数据/训练烟雾测试
├── scripts/              # 数据准备、训练、评估和报告脚本
├── reports/              # 可版本控制的汇总结果、图表与模型卡（不含敏感数据）
└── README.md
```

`.gitignore` 不再整体排除 `data/`，以便两名成员在仓库内共享经批准、去标识化且允许再分发的数据。仍应排除 `artifacts/`、`checkpoints/`、`wandb/`、`.env`、模型大文件和实验临时输出；每份共享数据都必须附带来源、许可/伦理状态和版本说明。

## Git 忽略规则与调整

根目录的 [`.gitignore`](.gitignore) 用于避免将本地环境、敏感信息和不可复现的生成物提交到仓库。当前规则按以下范围生效：

| 类别 | 默认忽略内容 | 说明 |
| --- | --- | --- |
| 系统与 IDE | `.DS_Store`、`Thumbs.db`、`.idea/`、`.vscode/`、交换文件 | 不同成员本地开发工具产生的文件 |
| Python 环境 | `__pycache__/`、测试/类型检查缓存、`.venv/`、`venv/`、`env/` | 本机解释器和工具生成的临时内容 |
| 实验产物 | `artifacts/`、`checkpoints/`、`models/`、`outputs/`、`logs/`、`tmp/` | 模型权重和临时输出默认不提交；`data/` 不在忽略列表中 |
| 实验跟踪与缓存 | `wandb/`、`mlruns/`、`.dvc/cache/` | 实验平台运行目录和本地缓存 |
| 密钥与凭据 | `.env`、`secrets/`、`*.pem`、`*.key`、`credentials.json` | 访问令牌、证书和本地配置 |

以下内容明确允许提交：

- `data/` 下经批准、去标识化且允许仓库共享的数据（包括原始数据和合成样例）；
- `.env.example`、`.env.template` 等不含真实凭据的配置模板；
- `tests/fixtures/` 下用于测试的固定夹具；
- `docs/`、`configs/`、`src/`、`tests/`、`scripts/` 以及不含敏感信息的汇总报告。

成员调整规则时请遵循：

1. 优先添加精确的目录或文件模式，避免使用会误伤源码、配置或文档的宽泛规则。
2. 数据文件不会因目录名自动忽略。提交数据前必须确认去标识化、伦理审批、使用许可和再分发范围，并在文档中记录数据版本。
3. 用 `git check-ignore -v <路径>` 查看某个路径命中的规则，用 `git status --ignored` 检查整体效果。
4. `.gitignore` 只对尚未被 Git 跟踪的文件生效。若敏感文件已被误跟踪，应先从索引移除（如 `git rm --cached <路径>`），确认本地文件保留后再提交修复。
5. 需要共享的实验结果应提交可复现的配置、脚本和脱敏汇总；未经许可的个体记录或模型权重仍不得提交。

## 双人协作

模型开发由两名成员负责：一人主责数据管线、特征工程和基线模型；另一人主责多模态融合、评估解释和轻量化推理。两人先冻结数据与评估接口，再使用合成/公开样例并行开发，最后通过适配器完成一次集成；研究问题、终点定义、特征字典、数据切分、模型入选和对外结论由两人共同确认。

完整的分工、阶段门、数据规范、实验记录、Git 流程和合并标准见 [TEAM_CONVENTION.md](TEAM_CONVENTION.md)。
